# ООО «Маяк» — сайт. Техническая документация

Полное описание проекта для передачи другому ИИ / разработчику. Содержит стек,
структуру, модель данных, дизайн-систему, разбор ключевых фич, подводные камни,
деплой и список открытых задач.

---

## 1. О проекте

Корпоративный сайт компании **ООО «Маяк»** — производителя модульных и
металлических конструкций: бытовки, блок-контейнеры, модульные здания, хозблоки,
санитарные решения, металлоконструкции. Собственное производство в **Раменском
городском округе (деревня Рыбаки, Московская область)**. Основная зона доставки и
монтажа — до 300 км от производства.

Тип сайта: многостраничный маркетинговый сайт с интерактивным конфигуратором,
каталогом, формами заявок. Язык — русский.

Домен (прод): **https://mayak-modul.ru** — основной. Адрес
`mayak.alazarstudio.com` был техническим, для показа заказчику.

## 3. Запуск и сборка

```bash
npm install
npm run dev      # dev-сервер сайта
npm run dev:all  # БД в Docker + API админки + сайт одной командой
npm run build    # прод-сборка (next build)
npm run start    # прод-сервер после build
npm run lint     # eslint
```

`npm run dev:all` (`scripts/dev-all.mjs`) поднимает контейнер PostgreSQL, API админки
из `react-project-admin-back` (порт 5000) и сайт (порт 3199). Логи трёх процессов
идут в один поток с префиксами. Ctrl+C гасит сайт и API, контейнер БД остаётся.

**Важные нюансы окружения:**

- **Turbopack падает на кириллице в пути к проекту.** Локальный путь содержит
  кириллицу (`…/Документы/VSCODE/Сайт Маяк`), поэтому dev запускать на webpack:
  `next dev --webpack`. В проекте есть `.claude/launch.json` с готовой конфигурацией
  (webpack, порт **3199**). `next build` кириллицу переносит нормально.
- **Переменные окружения** — в `.env.local` (в `.gitignore`, в репозиторий не
  попадает). Нужна `NEXT_PUBLIC_YANDEX_MAPS_KEY` (ключ Яндекс.Карт для блока карты;
  в коде есть фолбэк-значение, но лучше задать свой ключ с разрешённым доменом).
- ОС разработки — Windows. Рабочее дерево в CRLF, `git archive`/репозиторий — LF
  (git об этом предупреждает, это нормально).

### Данные и утилиты (`src/lib`)

- `content.ts` — **слой чтения контента публичными страницами** (товары,
  статьи, направления, контакты, цифры, этапы, номера счётчиков, адреса для
  уведомлений о заявках). Ходит в API админки, кэширует
  с тегами и всегда имеет фолбэк на файлы ниже. Подробно — раздел 6.
  Формы данных — в `content-types.ts` (их импортируют и клиентские компоненты).
- `site.ts` — **эталонный контент и фолбэк**: `SITE_URL` (канонический домен для

  `FOOTER_NAV`, `SOLUTIONS` (7 направлений с карточками), `SOLUTION_PRODUCTS`,
  `PROCESS` (5 этапов), `STATS`.
- `catalog.ts` — эталонные товары каталога (16 шт.; у каждого `image` —
  обложка и `images` — галерея), типы (`ProductType`), фильтры
  (`PRODUCT_TYPES`, `CATALOG_SECTIONS` = типы + «Индивидуальные решения»,
  `EXPLOITATIONS`, `PRODUCT_OPTIONS`, `PURPOSE_TAGS`) и `productPath(slug)` —
  единственный источник адреса страницы товара (карточка, карта сайта, JSON-LD).
- `configurator-steps.ts` — шаги конструктора (назначение/тип/размер/окна/двери/
  отделка/инженерия).
- `configurator-assets.ts` — пути к рендерам конструктора, `bytovkaRender()`.
- `typo.ts` — микротипографика (см. раздел 7).
- `cn.ts` — `clsx + tailwind-merge`.
- `blog.ts` — эталонные статьи блога (`BLOG_ARTICLES`) и тип `BlogArticle`,
  к которому `content.ts` приводит ответы API. Импортов во время выполнения
  здесь быть не должно: файл напрямую импортирует Node-скрипт пересборки
  снимка сида.
- `media.ts` — общее для всех картинок сайта: тип `GalleryImage`
  (`{ src, alt }`), проверка пути `isLocalImagePath`, разбор произвольных
  данных `toGalleryImages` (терпит и старый формат из голых строк).
- `blog-blocks.ts` — блочная модель тела статьи (см. раздел 6): union
  `ArticleBlock` из десяти типов, русские названия типов, конвертер
  `toArticleBlocks`, транслитерация якорей `slugifyAnchor` (повторяет
  `slugify` бэкенда) и охранная проверка путей к картинкам
  `isLocalImagePath`.
- `lead-client.ts` — отправка заявки с клиента: сама подставляет `page`/`utm`,
  разбирает ответ и возвращает код ошибки (`rate_limited` / `failed`).
  **Все формы обязаны показывать экран успеха только при успешном ответе.**
- `lead-delivery.ts` — доставка заявки на сервере, разделена на две фазы:
  `saveLead` (база админки + JSONL-журнал + лог процесса) вызывается до ответа
  пользователю, `notifyLead` (Telegram + письмо) — после, через `after()`.
  Каналы независимы, сбой одного не мешает другим. Получатели Telegram —
  список из настроек панели, переменная `TELEGRAM_CHAT_ID` — запасной
  вариант; токен бота только из окружения (см. раздел 9).
- `telegram-chats.ts` — форма записи получателя Telegram (`{ chatId, label }`),
  проверка `chat_id`, разбор произвольных данных из jsonb и пределы (20
  получателей, 80 символов подписи). Без зависимостей: импортируется и
  серверной доставкой, и серверными экшенами панели, и клиентской формой.
- `admin/` — клиент API админки: `api.ts` (запросы с сервера), `session.ts`
  (JWT в httpOnly-cookie), `config.ts`, `types.ts`. В браузер токен не попадает.

Плюс `src/proxy.ts` — в этой версии Next так называется middleware; закрывает
`/admin/**` от неавторизованных.

## 6. Ключевые фичи и как они работают

### Видео-герой (`sections/Hero.tsx`)
Фоновое видео играет один раз, затем замирает на последнем кадре, который
«оживает» медленным ken-burns. Контент (заголовки, кнопка) и шапка появляются
синхронно на ~3-й секунде через событие `hero-revealed` + флаг `window.__heroRevealed`.
**Видео проигрывается один раз за визит**: флаг `mayak-hero-played` в
`sessionStorage`; при повторных заходах на главную видео не запускается (нет
`autoPlay`, `play()` вызывается вручную только на первом заходе), сразу
показывается `hero-lastframe.webp`. Стоп-кадр анимируется как `<Image>`, а не
видео — чтобы не было шиммера при масштабировании.

### Конфигуратор (`constructor/BytovkaConfigurator.tsx`)
Пошаговый подбор бытовки. Стратегия рендеров — **«по осям, а не по комбинациям»**:
экстерьеры для пар обшивка×цвет (профлист/вагонка × белый/серый/зелёный/синий),
интерьеры для видов отделки. При выборе двери/отделки основное превью НЕ меняется
(остаётся выбранный внешний вид), а увеличенное фото варианта показывается у
курсора. Зелёный/синий — монохром без бордового каркаса; все экстерьеры в едином
ракурсе. Итог → заявка через `/api/lead`.

### Анатомия (`sections/BlockContainerAnatomy.tsx`)
Тумблер «Снаружи/Внутри», кроссфейд выровненных рендеров, хотспоты с плавным
тултипом. Точки-координаты заданы в долях (0..1).

### Карта производства (`sections/ProductionMap.tsx`)
Яндекс.Карты JS API 2.1, статичная, тёмная (CSS-инверсия тайлов). Поверх — «радар»:
круг 300 км + вращающаяся развёртка. Размер радара точно считается из геометрии
круга. Ключ — `NEXT_PUBLIC_YANDEX_MAPS_KEY`.

### Микротипографика (`lib/typo.ts`)
Функция `typo(text)` расставляет неразрывные пробелы: смысловые связки
(«до 300 км», «под задачу»…), число+единица, не оставляет короткие предлоги/союзы
и тире в конце строки. **Применять только к отображаемому тексту, НЕ к значениям,
участвующим в логике** (ключи фильтров, сравнения) — иначе сломается сравнение строк.

### Модалки
Radix Dialog + кастомные `@keyframes` (классы `anim-modal`/`anim-overlay`).
`CallbackModal`, `SolutionModal`, `ProposalModal` (широкая, формат КП, приём ТЗ-файла).

### Страница товара (`/catalog/[slug]`)

У каждого товара свой адрес: `productPath(slug)` → `/catalog/<slug>`. Slug лежит
в `Product.id` (у статических товаров это человекочитаемый ключ, у товаров из
базы `content.ts` кладёт туда колонку `slug`).

Что на странице: хлебные крошки (`<Breadcrumbs current={…}/>` — проп нужен,
потому что человеческое название знает только страница), галерея
(`ProductGallery`), параметры (габариты, режим эксплуатации, тип, назначение),
опции, полное описание, комплектация, форма заявки (`LeadForm` с источником
`Заявка из каталога: <название>`) и до четырёх смежных товаров — сначала того же
типа, потом по совпадению сценариев, чтобы страница не была тупиковой.

**Всё содержимое отдаёт сервер.** До появления маршрута описания и комплектации
существовали только внутри модалки, то есть в разметке их не было вовсе, и
сослаться на товар было нечем — ни человеку, ни ИИ-поиску.

**Модалки товара больше нет.** `ProductModal` удалён: он показывал ровно то же
самое, что теперь есть на странице, и его сохранение означало бы два рендера
одних данных, второе место с текстом источника заявки и Radix Dialog + форму в
клиентском бандле каталога на все 16 карточек. В карточке ровно одна ссылка — на
названии, с растянутым `before:absolute before:inset-0`, поэтому кликается вся
карточка, а адрес можно скопировать. Ряд иконок-подсказок поднят над этим слоем
(`relative z-10`), иначе он перехватывал бы наведение.

**Разметка.** `Product` с `@id`/`url`, `sku` (это slug), картинками галереи,
`category`, `brand`/`manufacturer`, `additionalProperty` (габариты, режим,
назначение, тип изготовления, каждая опция и каждая строка комплектации) и
`offers` **без числовой цены** — цены индивидуальные и выдумывать их нельзя, но
валюта, продавец и доступность полезны (`PreOrder` у индивидуальных позиций,
`InStock` у типовых). Числовые `width`/`depth` ставятся только у точного размера
вида «6×2.4 м»; «от 12×6 м» и «по проекту» остаются текстовым свойством.
Тот же `@id` объявлен у позиции в `ItemList` на `/catalog` — записи склеиваются.

**Поведение как у блога:** `generateStaticParams` из базы с фолбэком на статику,
`dynamicParams` по умолчанию (товар из панели открывается без пересборки),
несуществующий и снятый с публикации slug → 404 (публичный список API отдаёт
только опубликованные). Товарные адреса попадают в `/sitemap.xml`.

### Сертификат / реквизиты
`CertificateCard` (превью + «Открыть PDF»), `CertificationBlock` (крупный блок:
слева превью + «Открыть PDF», справа чек-лист данных). PDF открывается, а не
скачивается — `next.config.ts` ставит `Content-Disposition: inline` для `/certs/`.

### Контент из админки (`lib/content.ts`)

Публичные страницы (`/`, `/catalog`, `/catalog/[slug]`, `/blog`, `/blog/[slug]`, контакты в шапке,
футере и на страницах) читают контент из базы админки — через единственный
модуль `src/lib/content.ts`. Три свойства, которые нельзя терять при правках:

1. **Фолбэк.** Ошибка сети, 4xx/5xx, таймаут (4 с) или пустой список → страница
   рисуется на статических данных из `src/lib/{site,catalog,blog}.ts`. Факт
   фолбэка пишется в серверный лог строкой `[content] <ресурс>: показываем
   статические данные — <причина>`. Прод без API продолжает работать.
2. **Кэш с тегами.** `unstable_cache` + теги `products` / `articles` /
   `solutions` / `settings`, ревалидация 300 с. Теги от `unstable_cache`
   поднимаются в кэш самой страницы, поэтому маршруты становятся ISR (в выводе
   `next build` у них Revalidate 5m). Cache Components (`cacheComponents: true`
   и `"use cache"`) НЕ включены: флаг переводит всё приложение на
   dynamic-by-default и требует Suspense вокруг каждого динамического куска.
3. **Мгновенное обновление.** Серверные экшены админки после успешного
   сохранения зовут `revalidateContent(...)` (`src/lib/admin/revalidate.ts`) —
   это `updateTag`, то есть немедленное истечение тега, а не
   stale-while-revalidate. Публичная страница показывает правку сразу.

Клиентским компонентам данные передаются пропсами; контакты — через
`ContactsProvider` (`useContacts()`), у которого свой статический фолбэк.

У номеров счётчиков (`getAnalytics`) и адресов уведомлений (`getLeadDelivery`)
фолбэк **пустой**, а не эталонный: этих значений в коде нет и быть не может —
они существуют только в базе. Недоступный API означает страницу без счётчиков,
а не сломанную страницу.

### Счётчики аналитики (`components/SiteAnalytics.tsx`)

Яндекс.Метрика и GA4 подключаются номерами из панели (Настройки → Настройка
метрик), каждый независимо; пустое значение — счётчика нет вовсе. Четыре
свойства, которые нельзя терять:

1. **Только публичные страницы.** Компонент подключён в layout группы
   `(frontend)`. У админки свой корневой layout (`src/app/(admin)/layout.tsx`),
   поэтому в `/admin` счётчиков нет: раздел под `noindex`, а визиты редактора
   завышали бы статистику.
2. **Стратегия `afterInteractive`** — значение по умолчанию `next/script` и
   рекомендованное документацией для аналитики: скрипт вставляется на клиенте
   после начала гидратации и не задерживает ни разметку, ни интерактивность.
   `beforeInteractive` тянул бы чужой скрипт вперёд собственного кода страницы.
3. **Формат проверяется перед подстановкой.** Номер уезжает во встроенный
   скрипт, то есть это исполняемый код, а не текст. Шаблоны (`^\d{1,12}$` и
   `^G-[A-Z0-9]{4,18}$`) повторяют проверку API и стоят в трёх местах: в форме
   панели, в серверном экшене и в самом компоненте — в базу можно записать что
   угодно и напрямую.
4. **Аналитика не роняет страницу.** Недоступный API → пустые значения →
   счётчиков просто нет.

### Фотографии товара (`image` + `images`)

У товара два поля: `image` — **обложка** (её показывают карточка каталога,
карточки смежных товаров и метаданные `openGraph`) и `images` — **все фотографии в порядке
показа, включая обложку**, каждая как `{ src, alt }` (тип `GalleryImage` из
`lib/media.ts` — та же форма, что у блока «Галерея» в статье). Обложка обязана
входить в `images`, иначе API вернёт 400; за этим следят и панель, и
`content.ts`.

- Пути только локальные, от одного «/»: `next/image` на внешнем адресе
  бросает исключение и роняет страницу (см. `isLocalImagePath`).
- Дубликаты схлопываются по `src`, предел — 24 фотографии (`MAX_IMAGES`),
  длина описания — 300 символов (`MAX_ALT_LENGTH`).
- **Пустой `alt` — легальное значение** (декоративная картинка) и попадает в
  разметку как `alt=""`. Запасное описание (название товара) подставляется
  только там, где поля нет вовсе, — то есть у товаров в старом формате
  `images: string[]`. Затирать осознанно пустое описание нельзя.
- Описание файла в медиатеке — **значение по умолчанию**: при вставке
  копируется к фотографии товара и дальше живёт отдельно в обе стороны.
- У товаров, созданных до появления галереи, `images` пуст — `toGallery` в
  `content.ts` собирает галерею из одной обложки, а `ProductGallery` в этом
  случае рисует просто картинку, без стрелок и ленты миниатюр.

Редактор — `components/admin/GalleryEditor.tsx` (множественная загрузка по
одному файлу за запрос с прогрессом, выбор обложки радиокнопкой, порядок,
удаление). Просмотр — `components/catalog/ProductGallery.tsx` на странице товара.

### Блочная модель статьи блога (`lib/blog-blocks.ts`)

Тело статьи — последовательность блоков, а не секций фиксированной формы.
Каждый блок это объект с уникальным в пределах статьи `id` (он же якорь у
заголовка) и `type`; типов десять:

| `type` | Поля |
|---|---|
| `heading` | `text`, `level?` (2 — раздел, 3 — подзаголовок; нет поля = 2) |
| `text` | `paragraphs: string[]` |
| `list` | `items: string[]`, `ordered?` |
| `table` | `headers: string[]`, `rows: string[][]`, `caption?` |
| `quote` | `text`, `author?` |
| `image` | `src`, `alt`, `caption?` |
| `gallery` | `images: { src, alt }[]` |
| `video` | `src`, `poster?`, `caption?` |
| `file` | `url`, `title` |
| `accordion` | `items: { question, answer }[]` |

Схема согласована с валидацией API (`react-project-admin-back/app/article/
article-blocks.js`) — правки вносятся в обе стороны одновременно.

Три вещи, которые нельзя терять при доработках:

1. **Имя поля — `sections`.** Так называется колонка jsonb в базе, так же поле
   уходит в API и так же адресуют его сообщения об ошибках (`sections[N]
   (type "…")`). Переименование сломало бы снимок сида и миграции ради
   косметики, поэтому `BlogArticle.sections` — это массив `ArticleBlock`.
2. **Конвертер старого формата работает на чтении.** Статьи, созданные до
   перехода на блоки, лежат в базе секциями `{ id, title, paragraphs?,
   bullets?, table? }`. `toArticleBlocks` разворачивает такую секцию в
   `heading` + `text` + `list` + `table` (только для заполненных полей),
   отдавая `id` секции заголовку — якоря и оглавление продолжают работать.
   Конвертер вызывается и в `content.ts`, и в форме админки, и терпим к
   мусору: битый блок пропускается, страница не падает. Строгую проверку с
   понятной ошибкой делает API при сохранении.
3. **Ячейки таблицы позиционные.** Пустая ячейка в середине строки
   сохраняется, длина строки выравнивается по числу заголовков. Иначе столбцы
   съезжают под чужие заголовки — данные молча портятся.
4. **Картинка блока — только локальный путь** (`isLocalImagePath`). `next/image`
   без хоста в `images.remotePatterns` не рисует внешний адрес, а бросает
   исключение — и падает вся страница статьи. Закрыто с двух сторон: панель не
   даёт сохранить внешний адрес, а конвертер и `ArticleBody` такие картинки
   отбрасывают, чтобы никакое значение в базе не роняло публичную страницу.
   На `video.src`, `video.poster` и `file.url` правило не распространяется:
   это обычные атрибуты `<video>`/`<a>`, уронить страницу они не могут.

Рендер — `components/blog/ArticleBody.tsx` (аккордеон на нативном `<details>`,
поэтому доступен с клавиатуры и работает без JS). Редактор — блочный,
`app/(admin)/admin/(panel)/blog/BlocksEditor.tsx`, см. `docs/ADMIN.md`.

**Иерархия заголовков.** На странице ровно один `<h1>` — заголовок статьи,
поэтому тело статьи начинается с `<h2>`. Блок «Заголовок» рисуется `<h2>`
(раздел) или `<h3>` (подзаголовок) по полю `level`; глубже не идём, пропусков
уровней быть не должно. Оглавление статьи (`articleOutline`) вкладывает H3
внутрь своего H2, а не мешает их в плоский список. То же правило действует на
всех публичных страницах: подвал даёт три `<h2>` на каждой странице, у списка
товаров каталога есть свой `<h2>` (визуально скрытый, `sr-only`) перед
карточками-`<h3>`.

### Картинки медиатеки (`/uploads/[...path]`)

Файлы, загруженные в админке, лежат рядом с API и в базе записаны как
`/uploads/…webp`. Публичный роут `src/app/(frontend)/uploads/[...path]/route.ts`
стримит их с API на свой домен: путь из базы работает как есть, `next/image`
считает его локальным, а `remotePatterns` не нужны (адрес API — переменная
окружения, а не константа сборки, и API отдаёт статику с
`Cross-Origin-Resource-Policy: same-site`). Наружу пропускаются только
растровые расширения, `..` в пути отбрасывается. Админка продолжает ходить в
`/admin/uploads/*` — там прокси под авторизацией.

## 7. Подводные камни (важно для правок)

1. **`next build` жёстко проверяет типы, dev — нет.** Типичная ловушка:
   framer-motion `ease: [0.22,1,0.36,1]` в ОТДЕЛЬНОЙ константе выводится как
   `number[]` и не подходит под `Variants`. Решение — аннотировать константу
   `const x: Variants = {...}` (в JSX инлайн-transition типизируется контекстно и
   проходит).
2. **`next/image` кэширует по URL.** Query-строки (`?v=2`) в localPatterns
   запрещены — при обновлении картинки **меняем имя файла** (`-v2`, `-v3`).
3. **Неразрывные пробелы (U+00A0)** визуально неотличимы от обычных. Проверять
   наличие/отсутствие только программно (в JS-регексе escape ` `, литерал в
   heredoc/командной строке теряется). `\b` в JS-регексе НЕ работает с кириллицей.
4. **framer-motion + скрытая вкладка:** анимации на `requestAnimationFrame` не
   идут, если страница скрыта (напр. фоновая/headless-панель). Видео и React-стейт
   при этом работают. Это артефакт окружения, НЕ баг — в видимой вкладке всё ок.
5. **Ненастроенный канал доставки заявки молча пропускается.** Это осознанно:
   заявка не должна теряться из-за одного отвалившегося канала. Обратная
   сторона — отсутствие уведомлений выглядит как «всё работает». См. раздел 9.
6. **Сегмент маршрута `/constructor` ломает dev-оверлей Next 16.2.9.** Это баг
   самого Next: обозреватель сегментов складывает пути в объект-словарь, и ключ
   `constructor` попадает в `Object.prototype.constructor` — обход дерева
   проваливается и страница падает с `Cannot read properties of undefined
   (reading 'page.tsx')`. Только dev, прод-сборка не затронута. Обход —
   `src/components/dev/DevSegmentExplorerGuard.tsx` (подключён в layout, из
   прод-бандла вырезается). Затрагивает любые сегменты с именами из
   `Object.prototype` (`toString`, `valueOf`, `hasOwnProperty`…). При обновлении
   Next проверить, не починили ли — тогда обход удалить.
7. **`.next-stale-cms/`** — мусор от откаченной интеграции CMS. Папка попадала
   под проверку eslint и валила `npm run lint` сотнями ошибок; добавлена в
   `globalIgnores` в `eslint.config.mjs`.
8. **Закрытая панель мобильного меню раздувала ширину документа.** Она стоит за
   правым краем через `translate-x-full`, и Chrome учитывал её в прокрутке: на
   ширинах около планшета/ноутбука на каждой странице появлялась горизонтальная
   полоса (документ 1582px при окне 806px). Лечится парой `overflow-x: clip` на
   `html` и `body` в `globals.css` — именно `clip`, а не `hidden`: он не создаёт
   контекст прокрутки и не ломает `position: sticky`. Одного правила на `html`
   недостаточно, нужны оба.

## 8. Деплой

Основной домен — **https://mayak-modul.ru**. На момент написания он ещё ничего
не отдаёт (сайт туда не выложен); работает технический адрес
**https://mayak.alazarstudio.com**, который использовали для показа заказчику.
Домен `mayak-modul.ru` обслуживается Beget: там же почта отправителя заявок
(MX `mx1.beget.com`) и A-запись `83.222.18.100`.

Текущая площадка технического адреса: сервер Ubuntu 22.04, приложение в
`/var/www/mayak`, запущено через **pm2** (app `mayak`, порт 3000, `npm run start`),
за **nginx** (reverse-proxy), SSL — Let's Encrypt (авто-редирект и авто-продление),
ufw 22/80/443. Учётные данные сервера и SSH-детали — вне репозитория.
**Где будет жить основной домен — на этом же сервере или на хостинге Beget —
не решено;** от этого зависит порядок выкладки, см. `docs/DEPLOY.md`.

Подробная инструкция — **`docs/DEPLOY.md`** (включая первую установку API
админки, требования к nginx и включение уведомлений о заявках).

**Выкладка обновлений** (репозиторий приватный, `git clone` на сервере без токена
не работает):
1. `git archive --format=tar.gz -o mayak.tar.gz HEAD`
2. скопировать на сервер (pscp/scp), распаковать в `/var/www/mayak` (не трогает
   `node_modules`/`.env.local`)
3. `npm ci` (если менялись зависимости) → `npm run build` → `pm2 restart mayak`

Долгую `npm run build` на сервере запускать детачно (`setsid … >build.log`; статус
опрашивать по маркер-файлу, НЕ через `pgrep 'next build'` — ложно матчит сам себя).
На сервере есть swap (RAM ~2 ГБ, иначе сборка падает по памяти).

## 9. Формы заявок

Все шесть точек отправки (LeadForm, CallbackModal, SolutionModal, ProposalModal,
`BytovkaConfigurator`, легаси-`Constructor`) шлют POST на `/api/lead` через
`lib/lead-client.ts`.

**На эндпоинте** (`app/(frontend)/api/lead/route.ts`): валидация zod, honeypot-поле
`company` (непустое → заявка тихо отбрасывается), лимит 5 заявок с IP за 10 минут
(429). Дальше `lib/lead-delivery.ts` рассылает заявку по всем настроенным каналам
независимо друг от друга — сбой одного не мешает остальным:

| Канал | Фаза | Где настраивается | Состояние |
|---|---|---|---|
| База админки | до ответа | `ADMIN_API_URL` + `ADMIN_SITE_API_KEY` | работает |
| JSONL-журнал | до ответа | `LEAD_LOG_FILE` | код готов, путь не задан |
| Лог процесса | до ответа | — | работает всегда (`[LEAD] {…}` в pm2) |
| Telegram | после ответа | токен — `TELEGRAM_BOT_TOKEN` (только окружение), получатели — список в панели, откат на устаревшее одиночное поле и `TELEGRAM_CHAT_ID` | токен задан (`@mayak_modul_bot`), список получателей правится в панели |
| Email | после ответа | SMTP — `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM` (только окружение), получатель — панель, откат на `LEAD_EMAIL` | настроен: `site@mayak-modul.ru` через `smtp.beget.com`, авторизация проверена |

**Ответ пользователю не зависит от внешних сервисов.** До ответа дожидаются
только каналы, которые ЗАПИСЫВАЮТ заявку: они локальные (API админки — сосед
по машине, журнал — файл) и укладываются в десятки миллисекунд. Уведомления
наружу уходят уже после ответа — через `after()` из `next/server`
(`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md`).
Раньше посетитель ждал у крутилки все 8 секунд таймаута зависшего SMTP;
измеренный ответ `POST /api/lead` при молчащем почтовом сервере: было
8,06–8,10 с, стало 13–130 мс.

Заявка при этом не может потеряться незаметно: строка `[LEAD] {…}` печатается
до ответа и ни от какой сети не зависит, так что успешный ответ всегда
означает записанную заявку. Результат уведомлений печатается отдельной строкой
`[LEAD] уведомления {…}` (связь по `receivedAt`) — одной общей строкой их не
собрать, не задержав главную запись на те же 8 секунд.

**Получателей в Telegram может быть несколько** — до 20, каждый с подписью
«кто это» (`src/lib/telegram-chats.ts`). Отправки идут параллельно и
независимо: заблокировавший бота получатель не мешает остальным, а в логе
виден результат по каждому. В панели есть помощник «Узнать chat_id»: он
опрашивает `getUpdates` токеном из окружения и показывает чаты, из которых
боту недавно писали; токен в браузер не попадает.

**Разделение секрета и адреса — общее правило обоих внешних каналов.** Адрес
получателя правится в панели (Настройки → Настройка заявок) и **имеет
приоритет** над переменной окружения; переменная осталась запасным вариантом
на случай незаполненной панели или недоступного API. Доступ к сервису
(токен бота, пароль SMTP) живёт только в `.env.local`, шаблон — в
`.env.example`: база уезжает в резервные копии, а утёкший оттуда секрет уже не
отозвать. В логе процесса рядом со статусом печатается выбранный адрес и его
источник — иначе «не настроен» не отличить от «настроен не туда».

**Почта — `nodemailer`, письмо текстовое.** HTML-части нет намеренно: главное
содержимое письма — комментарий со спецификацией из конструктора,
многострочный, и в `text/plain` он доходит ровно таким, каким его собрали. В
HTML пришлось бы экранировать его и разворачивать переносы в `<br>` — лишний
формат, который можно испортить. Заодно исчезает целый класс ошибок с
экранированием. Кодировку и RFC 2047 для кириллицы в теме берёт на себя
nodemailer. Транспорт создаётся на каждую отправку (заявки редкие, пул держал
бы TCP-соединение часами), три таймаута (`connectionTimeout`,
`greetingTimeout`, `socketTimeout`) по 8 с — зависший почтовый сервер не
задержит ответ пользователю дольше.

**`Promise.all` в `deliverLead` безопасен только потому, что ни один канал не
бросает исключение** — каждый ловит своё и возвращает результат значением.
Начни какой-нибудь бросать — `Promise.all` отклонится целиком, и пользователь
получит ошибку из-за сбоя второстепенного канала при уже сохранённой заявке.

**На клиенте:** экран «Заявка отправлена» показывается только при успешном ответе.
При 429 и при сетевой ошибке пользователь видит сообщение с телефоном, введённые
данные сохраняются, отправку можно повторить.

**Согласие на обработку персональных данных** оформлено подписью под кнопкой
(«Нажимая кнопку, вы соглашаетесь…»), а НЕ чекбоксом — во всех шести формах.
По 152-ФЗ согласие должно быть явным и активным действием, поэтому вопрос
вынесен в раздел 10 как юридический.

## 11. Админка

Панель управления контентом и заявками: интерфейс — в этом же приложении
(`src/app/(admin)/admin/**`), данные — в отдельном REST API
(`react-project-admin-back/`, Express + Prisma + PostgreSQL 17 в Docker).
Запуск всего окружения — `npm run dev:all`, панель на `/admin`.

Полное описание, доступы, разделы и ограничения — **`docs/ADMIN.md`**.
Документация самого API — `react-project-admin-back/README.md`.

Ключевое для разработки сайта:

- JWT лежит в **httpOnly-cookie**, в клиентский JS не попадает; все запросы к API
  идут с сервера (server components / server actions / route handlers).
- Публичный сайт и панель делят одно приложение, но не делят бандлы: в HTML
  публичных страниц клиентских чанков админки нет.
- В базе лежит копия контента из `src/lib/*.ts`, залитая идемпотентным сидом.
  Сид — способ вернуть контент в эталонное состояние после экспериментов.
- **Публичные страницы читают контент из базы** через `src/lib/content.ts`
  (см. раздел 6): правка в панели видна на сайте сразу, а при недоступном API
  сайт откатывается на статические данные из `src/lib/*.ts`.
- Разделы: Заявки, Каталог, Блог, **Главная** (табы «Направления» / «Цифры
  доверия» / «Этапы работы», адрес `/admin/solutions`), **Настройки** (табы
  «Контакты» / «Настройка метрик» / «Настройка заявок»), Медиатека.
  Табы — `src/components/admin/Tabs.tsx` на `@radix-ui/react-tabs`: выбранный
  таб хранится в адресе (`?tab=…`) через нативный `history.replaceState`
  (без похода на сервер), панели не размонтируются (`forceMount`), поэтому
  несохранённые правки переживают переключение.

## 12. Быстрый старт для нового ИИ/разработчика

1. Прочитать этот файл. Главное правило: это **не тот Next.js**, что в
   обучающих данных и в большинстве статей, — перед нетривиальным кодом
   смотреть `node_modules/next/dist/docs/`.
2. `npm install`, затем dev на webpack (кириллица в пути): порт 3199.
   Если нужна админка — `npm run dev:all` (поднимет БД и API).
3. Контент правится в админке (`/admin`), а `src/lib/site.ts` / `catalog.ts` /
   `blog.ts` остаются эталоном и фолбэком (правку там подхватит сид); страницы — в
   `src/app/**/page.tsx`; блоки — в `src/components/sections`.
4. Любой отображаемый русский текст оборачивать в `typo(...)`.
5. Перед коммитом: `npx tsc --noEmit` (устаревшие типы в `.next/types` лечатся
   `rm -rf .next/types .next/dev/types`), `npm run build`, `npx eslint src`.
