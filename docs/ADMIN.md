# Админка «Маяка»

Панель управления контентом и заявками. Состоит из двух частей:

| Часть | Где | Что делает |
|---|---|---|
| Интерфейс | `src/app/(admin)/admin/**` внутри сайта | страницы панели, вход, формы |
| REST API | `react-project-admin-back/` (отдельный проект) | данные, авторизация, загрузка файлов |
| База | PostgreSQL 17 в Docker | контейнер `mayak-postgres`, порт **5434** |

Интерфейс живёт в том же Next-приложении, что и сайт, но в отдельной группе
роутов со своим layout — шапки, футера и карты там нет. Браузер ходит только на
свой домен: JWT лежит в httpOnly-cookie, все обращения к API идут с сервера.

---

## Быстрый старт

```bash
npm run dev:all
```

Поднимает контейнер БД, API админки (порт 5000) и сайт (порт 3199) одной
командой, логи трёх процессов идут в один поток с префиксами.

- Сайт — http://localhost:3199
- Панель — http://localhost:3199/admin
- API — http://localhost:5000 (проверка живости: `GET /api/health`)

### Первый запуск на новой машине

Три шага, которые делаются один раз (без них `npm run dev:all` поднимет только
сайт и честно напишет об этом в лог):

```bash
docker compose -f react-project-admin-back/docker-compose.yml up -d
```

```bash
cd react-project-admin-back && npm install
```

Затем скопировать `react-project-admin-back/.env.example` в `.env`, заполнить
`DATABASE_URL`, `JWT_SECRET` и `SITE_API_KEY` (последний продублировать в
`.env.local` сайта как `ADMIN_SITE_API_KEY`) и залить данные:

```bash
cd react-project-admin-back && npx prisma migrate deploy && npm run seed
```

Запустить части по отдельности:

```bash
npm run dev -- --webpack -p 3199
```

```bash
cd react-project-admin-back && npm run dev
```

## Разделы панели

| Раздел | Что можно |
|---|---|
| Заявки | список с фильтром по статусу, смена статуса (Новая / В работе / Обработана / Спам), удаление |
| Каталог | товары: все поля, фотографии с выбором обложки, публикация, порядок; теги и опции — выбором из справочника. У каждого товара своя страница на сайте — `сайт.ру/catalog/<slug>` |
| Блог | статьи и тело из блоков (см. ниже): добавление по типу, перестановка, удаление |
| **Главная** | блоки главной страницы сайта, три таба: **Направления**, **Цифры доверия**, **Этапы работы** |
| **Настройки** | три таба: **Контакты**, **Настройка метрик**, **Настройка заявок** |
| Медиатека | загрузка изображений пачкой (перекодируются в WebP), имя файла и описание (alt) у каждого файла после загрузки, список, копирование пути |

### Табы: как они устроены

Разделы «Главная» и «Настройки» разбиты на табы. Три вещи, о которых полезно
знать:

- **Выбранный таб виден в адресе** — `?tab=stats`. Перезагрузка страницы,
  «назад» из формы направления и ссылка, отправленная коллеге, открывают тот
  же таб. Незнакомое значение в адресе просто открывает первый таб.
- **Клавиатура работает целиком**: Tab ставит фокус на группу табов, стрелки
  «влево»/«вправо» перебирают их, следующий Tab уводит внутрь панели.
- **Переключение не теряет введённое.** Формы в неактивных табах остаются в
  памяти страницы: можно начать править контакты, заглянуть в метрики и
  вернуться — текст будет на месте. Но это ещё **не сохранение**: закрытие
  вкладки или перезагрузка правки потеряют, у каждого таба своя кнопка
  «Сохранить», и нажимать её надо в каждом.

## Раздел «Главная»

Всё, что редактируется здесь, выводится на главной странице сайта.

| Таб | Что настраивается |
|---|---|
| Направления | блок «Решения по задачам»: вкладки, описание направления, буллиты и товары-примеры |

показывает ошибку, соседние продолжают работать.

## Раздел «Настройки»

| Таб | Что настраивается |
|---|---|
| Контакты | телефоны (по одному на строку), Telegram, MAX, e-mail, адрес производства |
| Настройка метрик | номер счётчика Яндекс.Метрики и идентификатор Google Analytics 4 |
| Настройка заявок | список получателей в Telegram и адрес почты, куда сообщать о новых заявках |

### Настройка метрик

Оба поля **необязательные и независимые**: заполнено — счётчик подключается,
пусто — не подключается вовсе (ни тега на странице, ни обращения к чужому
домену).

- **Яндекс.Метрика** — номер счётчика, только цифры (в Метрике: Настройка →
  Номер счётчика).
- **Google Analytics 4** — идентификатор потока вида `G-XXXXXXXXXX`. Старые
  идентификаторы Universal Analytics (`UA-12345`) не поддерживаются — Google
  их отключил.

Правка применяется **сразу**, без пересборки и перезапуска сайта.

Счётчики работают только на публичных страницах. **В `/admin` их нет
намеренно**: раздел закрыт от индексации, а визиты редактора завышали бы
статистику посещаемости. Если API настроек недоступен, страница рисуется без
счётчиков — из-за аналитики сайт не падает.

### Настройка заявок

Заявка с сайта дублируется в три места: раздел «Заявки» (база), Telegram и
почта. Здесь настраивается **куда** её слать во втором и третьем случае. Сама
заявка в любом случае попадает в «Заявки» и в журнал сервера — эти поля на её
сохранение не влияют.

- **Получатели в Telegram** — это **список**, а не одно поле: уведомление
  уходит каждому из него. Подробно — ниже.
- **Почта для уведомлений** — адрес, на который придёт письмо о новой заявке.

#### Список получателей в Telegram

Получателей может быть до **20**. У каждого две части:

- **подпись** — «кто это», до 80 символов («Максим», «Общий чат отдела
  продаж»). На доставку не влияет, но без неё список из четырёх голых чисел
  невозможно обслуживать;
- **chat_id** — число (у группы отрицательное и длинное, например
  `-1001234567890`) либо `@username` канала.

Кнопка **«+ Добавить получателя»** заводит пустую строку, **«Удалить»** —
убирает строку. Изменения вступают в силу после кнопки «Сохранить», сразу и
без пересборки сайта.

**Получатели независимы.** Заявка отправляется каждому отдельно: если один
заблокировал бота или в его `chat_id` опечатка, остальные всё равно получат
уведомление. В логе сервера видно результат по каждому.

Панель не даст сохранить список, если в нём есть ошибка, и покажет **все**
проблемы сразу, а не только первую:

| Что не так | Сообщение |
|---|---|
| строка добавлена, `chat_id` не заполнен | «Получатель N: не заполнен chat_id.» |
| в `chat_id` не число и не `@username` | «Получатель N: chat_id должен быть числом…» |
| подпись длиннее 80 символов | «Получатель N: подпись длиннее 80 символов.» |
| тот же `chat_id` уже есть выше | «Получатель N: этот chat_id уже есть в списке выше.» |

**Пустой список — законное состояние**, панель его сохранит. Это значит «в
Telegram не уведомляем»; на сами заявки не влияет — они всё равно в разделе
«Заявки», в журнале и на почте. Если при этом в базе ещё лежит старая
одиночная настройка, панель об этом честно пишет: уведомления пока уходят по
ней.

#### Кнопка «Узнать chat_id»

Telegram нигде не показывает `chat_id` в интерфейсе, поэтому его спрашивают у
самого бота. Кнопка открывает окно со списком чатов, из которых боту **недавно
писали** (Telegram помнит их около суток), — выберите нужный, и он добавится в
список получателей вместе с названием в качестве подписи. Уже добавленные
помечены «Уже в списке».

Как сделать, чтобы нужный чат появился в этом окне:

- **личный чат** — откройте бота в Telegram и отправьте ему любое сообщение
  (например «Старт»);
- **общий чат отдела** — создайте группу, добавьте в неё бота и напишите в
  группе любое сообщение. Только после сообщения бот узнаёт про группу.

После этого нажмите «Обновить». Если чатов нет вовсе, окно так и пишет и
объясняет эти два шага. Другие ответы тоже переведены на человеческий язык:
не задан токен бота, Telegram не принял токен, у бота настроен вебхук
(в этом случае опрос недоступен и `chat_id` придётся ввести руками), нет связи
с Telegram.

Токен бота при этом **остаётся на сервере**: в браузер уходит только готовый
список чатов.

**Здесь только адреса, доступы — в настройках сервера.** Правило одно для
обоих каналов: куда слать — в панели, чем слать — в переменных окружения
(файл `.env.local`, на проде — см. `docs/DEPLOY.md`). В панель доступы не
выносятся: база уезжает в резервные копии, а утёкший оттуда пароль уже не
отозвать.

| Канал | Адрес (панель) | Запасной адрес | Доступ (только окружение) |
|---|---|---|---|
| Telegram | список получателей | устаревшее одиночное поле, затем `TELEGRAM_CHAT_ID` | `TELEGRAM_BOT_TOKEN` |
| Почта | адрес получателя | `LEAD_EMAIL` | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` |

**Значение из панели всегда в приоритете**; запасной адрес из окружения
срабатывает, только когда поле здесь пустое.

**Пока доступ не настроен, канал молча пропускается** — это не ошибка. На
сохранение заявки это не влияет: она всё равно в «Заявках» и в журнале.
Каналы независимы, сбой одного не мешает остальным.

**Про почту.** Письма отправляются с отдельного ящика `site@mayak-modul.ru`,
а `companymayak@mail.ru` их только принимает. Домен `mayak-modul.ru`
обслуживается почтой Beget, поэтому сервер — `smtp.beget.com`, порт 465, и
`SMTP_PASSWORD` — **обычный пароль ящика**. Пароль внешнего приложения
понадобился бы, если бы отправляли через mail.ru; мы через него не отправляем.
Доступ прописан в `.env.local` и проверен: соединение и авторизация проходят.

**Что приходит в письме.** Тема — «Новая заявка с сайта — <источник>»; тело —
имя, телефон, время, комментарий, страница и utm. Письмо текстовое, без
оформления: комментарий из конструктора многострочный, и в текстовом виде
спецификация доходит ровно такой, какой её собрали.

**Многострочные поля.** Там, где значение — список произвольного текста
(комплектация, ключевые слова, буллиты, пункты), каждый элемент пишется с новой
строки. Запятые внутри пункта сохраняются: «Электрика: автомат, розетки, свет» —
это один пункт. Поля, у которых есть справочник (тип, режим эксплуатации, теги,
опции товара, иконки), вводом текста не заполняются — только выбором.

**Переносы строк значимы** в подписях направлений, цифр и этапов: они верстают
карточки на сайте. Поля для них многострочные — не склеивайте строки.

## Каталог: фотографии товара и обложка

У товара может быть **до 24 фотографий**. Все они лежат в одном наборе в
порядке показа, и одна из них помечена **обложкой**.

- **Обложку** показывают карточка каталога, карточки «Похожие решения» на
  страницах других товаров, структурированные данные для поисковиков и картинка
  в ссылке при пересылке в мессенджер. Она всегда входит в набор.
- **Остальные фотографии** складываются в галерею на странице товара
  (`сайт.ру/catalog/<slug>`): стрелки, лента миниатюр и счётчик «2 / 5». Если
  фотография одна, галерея не показывается вовсе — просто картинка.

**Описание (alt).** У каждой фотографии своё поле «Описание (alt)» — это текст,
который читают поисковики и те, кто картинку не видит (скринридер, отключённые
изображения, не загрузившийся файл). Описание привязано к своей фотографии и
переезжает вместе с ней при перестановке, смене обложки и удалении соседей.
Пустое описание допускается: так помечают чисто декоративную картинку, и на
сайте она получает `alt=""`. Панель мягко подсказывает заполнить, но сохранить
не мешает.

**Как загрузить.** Кнопка «Загрузить фотографии» принимает **сразу несколько
файлов**. Медиатека умеет принимать только по одному файлу за запрос, поэтому
панель отправляет их по очереди и показывает «Загружено 3 из 7». Если какой-то
файл не примут (например, это не картинка), остальные всё равно добавятся, а
про неудачный будет написано, какой именно и почему. Описание при загрузке не
спрашивается — его вводят потом, в поле под миниатюрой каждой фотографии.

Кнопка «Из медиатеки» добавляет уже загруженный ранее файл; в самом диалоге
тоже можно загрузить новые файлы — они встают первыми в списке с бейджем
«Только что», и описание у каждого правится там же.

У фотографии, добавленной из медиатеки, описание подставляется из медиатеки —
как значение по умолчанию. Дальше оно живёт у товара отдельно: правка описания
у товара медиатеку не меняет, и наоборот.

**Обложка** отмечается переключателем под миниатюрой — она одна, поэтому это
радиокнопка. Выбранная фотография получает бордовую рамку и бейдж «Обложка».

**Порядок** меняется стрелками «←» и «→» под миниатюрой: он же будет порядком
показа в галерее на сайте.

**Умолчания и ограничения:**

- первая добавленная фотография автоматически становится обложкой;
- если удалить обложку, роль переходит к первой оставшейся фотографии;
- **последнюю фотографию удалить нельзя** — обложка обязательна, а брать её
  будет неоткуда. Загрузите вторую, тогда лишнюю можно убрать;
- дубликаты не добавляются повторно, предел — 24 фотографии;
- путь должен вести на файл этого сайта. Ссылку на чужой сайт вставить нельзя:
  `next/image` внешний адрес не рисует, а роняет страницу.

У товаров, заведённых до появления галереи, набор фотографий пуст — сайт
показывает одну обложку, а панель предложит добавить остальные.

## Блог: тело статьи из блоков

Шапка статьи (заголовок, slug, SEO-описание, анонс, обложка, даты, вступление,
ключевые слова) заполняется полями формы. **Тело статьи собирается из блоков.**

Кнопка **«+ Добавить блок»** внизу открывает меню типов с иконками; клик по типу
добавляет пустой блок нужного вида в конец статьи. **Между блоками есть точки
вставки** — тонкая линия с «+ Блок сюда»: она добавляет блок именно в это место,
без перетаскивания стрелками через всю статью. Точка вставки — обычная кнопка,
она стоит в порядке обхода Tab сразу после последнего поля предыдущего блока, а
после добавления фокус переходит в первое поле нового блока.

У каждого блока свои поля, кнопки «↑ Выше» / «↓ Ниже» и удаление с
подтверждением. Порядок блоков в форме — это и есть порядок на странице.

| Тип | Что задаётся | Как выглядит на сайте |
|---|---|---|
| Заголовок | текст, **уровень**, якорь (id) | `<h2>` раздела или `<h3>` подзаголовка; разделы попадают в оглавление справа |
| Текст | абзацы (по одному на строку) | основной текст статьи |
| Список | пункты (по одному на строку), флажок «нумерованный» | карточка со списком; маркеры или номера |
| Таблица | заголовки столбцов, строки, подпись | таблица с бордовой шапкой, прокрутка внутри блока |
| Цитата | текст, автор | выделенная реплика с бордовой линией слева |
| Изображение | файл, alt, подпись | картинка 16:9 с подписью под ней |
| Галерея | список «файл + alt» | сетка картинок 4:3, две колонки от 640 px |
| Видео | ссылка на файл, постер, подпись | плеер с элементами управления |
| Файл | ссылка, название | карточка-ссылка «Открыть документ» |
| Аккордеон | пары «вопрос + ответ» | раскрывающиеся пункты, доступны с клавиатуры |

**Уровень заголовка.** H1 на странице ровно один — это заголовок самой статьи,
поэтому в теле статьи доступны только два уровня:

- **Раздел (H2)** — крупный заголовок, пункт оглавления. Значение по умолчанию.
- **Подзаголовок (H3)** — делит раздел на части, кегль меньше, в оглавлении
  показывается вложенным под своим разделом.

Глубже не идём: `H4` и ниже ломают SEO-иерархию, и выбрать их нельзя. Уровни
нельзя перепрыгивать — подзаголовок всегда живёт внутри раздела; если H3
оказался раньше первого H2, сайт покажет его отдельным пунктом оглавления,
чтобы он не потерялся. У заголовков в статьях старого формата уровень H2.

**Обязательные поля.** Пустой блок API не примет: заголовку нужен текст, тексту
— хотя бы один абзац, списку — хотя бы один пункт, таблице — хотя бы один
заголовок столбца, изображению — файл и alt, файлу — ссылка и название,
галерее и аккордеону — хотя бы один заполненный элемент. Панель проверяет это до
отправки, **перечисляет все найденные проблемы разом**, подсвечивает проблемные
блоки, пишет причину прямо в блоке и прокручивает форму к первому из них.

**Якоря.** У каждого блока есть идентификатор, уникальный в пределах статьи. У
заголовка он редактируется: это адрес раздела после `#` и пункт оглавления.

У нового заголовка якорь собирается из текста транслитерацией («Как выбрать
утепление» → `kak-vybrat-uteplenie`) и при совпадении получает числовой суффикс.
Как только заголовок сохранён — или якорь поправили руками — он замирает и за
текстом больше не следует: адрес опубликованного раздела меняться сам не должен,
иначе побьются внешние ссылки. В якоре допустимы только строчные латинские
буквы, цифры и дефис; пробелы и кириллицу панель сохранить не даст. У остальных
типов идентификатор выдаётся автоматически и в интерфейсе не показывается.

**Ячейки таблицы позиционные.** Каждая ячейка — отдельное поле; пустая ячейка в
середине строки сохраняется, и столбцы не съезжают под чужие заголовки. Любые
символы, включая «|», вводятся как есть.

Пустые столбец и строка удаляются сразу, заполненные — спрашивают
подтверждение. Отдельно предупреждает удаление **последнего** столбца: без
заголовков строки хранить негде, поэтому вместе с ним удаляется вся таблица.
Только что добавленный блок «Таблица» показывает нейтральную подсказку «Таблица
пуста», а не ошибку: красным он становится, если строки заполнены без
заголовков или после неудачной попытки сохранить.

**Изображения** (в блоках «Изображение», «Галерея» и постер видео) выбираются из
медиатеки или загружаются кнопкой — вручную путь вводить не нужно. **Ссылка на
картинку с чужого сайта запрещена**: путь должен начинаться с «/» и вести на
файл этого сайта. Панель такую статью не сохранит и объяснит почему —
`next/image` внешний адрес не рисует, а бросает исключение, и статья открывалась
бы с ошибкой 500. Нужную картинку надо загрузить в медиатеку.

**Видео и документы через медиатеку загрузить нельзя**: API принимает только
растровые изображения (см. «Ограничения»). Такие файлы выкладываются на сайт
отдельно (каталог `public/`), а в блоке указывается путь — например
`/certs/sertifikat.pdf`; здесь внешний адрес допустим, плеер и ссылка работают с
любым.

### Старый формат

Статьи, созданные до перехода на блоки, лежат в базе секциями вида
`{ id, title, paragraphs?, bullets?, table? }`. Мигрировать данные не нужно:
конвертер (`toArticleBlocks` в `src/lib/blog-blocks.ts`) разворачивает секцию в
`Заголовок` + `Текст` + `Список` + `Таблицу` (только для заполненных полей) при
каждом чтении — и на сайте, и при открытии формы. Идентификатор секции достаётся
заголовку, поэтому якоря и оглавление продолжают работать. Сохранение из панели
записывает статью уже в блочном виде.

В базе и в API список блоков по-прежнему называется `sections` (колонка jsonb),
и сообщения об ошибках адресуют блоки как `sections[N]` — панель переводит их в
«Блок N «Тип»: …».

## Медиатека: загрузка и описания файлов

**Порядок работы: сначала загрузили файлы, потом подписали каждый.** При
загрузке описание не спрашивается вовсе — ни у пачки, ни у одного файла: одна
подпись на несколько картинок ничего не описывает, а разводить два разных
сценария для «одного файла» и «нескольких» незачем.

**Загрузка.** Кнопка «Загрузить изображения» принимает сразу несколько файлов.
API медиатеки берёт по одному файлу за запрос, поэтому панель отправляет их по
очереди и показывает «Загружено 3 из 7». Если какой-то файл не примут (например,
это не картинка), остальные всё равно загрузятся, а про неудачный будет сказано,
какой именно и почему.

**Сразу после загрузки** файлы собираются в отдельный блок над списком — с
бордовой рамкой, бейджем «Только что» и призывом заполнить описание. Искать их в
общем списке не нужно, а фокус уезжает в поле описания первого загруженного
файла: можно печатать, не трогая мышь. Enter в поле сохраняет описание, Tab
уводит дальше по карточке. Кнопка «Готово, свернуть» убирает блок, и файлы
переезжают в общий список. Перезагружать страницу не нужно ни разу.

**У каждого файла своё поле «Описание (alt)» и своя кнопка «Сохранить
описание».** После успешного сохранения рядом появляется отметка «сохранено»,
при неудаче — текст ошибки по-русски прямо под полем. Пустое описание сохранять
не мешает: так помечают декоративную картинку, подсказка про заполнение —
мягкая. Описание файла правится и в диалоге выбора файла (кнопка «Из
медиатеки»), чтобы не уходить в раздел ради одной строки.

**В диалоге выбора файла** всё устроено так же: кнопка «Загрузить файлы»
принимает несколько файлов без общего описания, загруженные встают первыми в
списке с бейджем «Только что», у каждого — своё поле описания и своё
сохранение.

**Имя файла правится там же — поле «Имя файла» над описанием.** Загрузка даёт
имя вида `IMG_3421-1785274…webp`: осмысленное задают руками. Имя попадает в
адрес картинки, а адрес читают и люди, и поисковики, поэтому «bytovka-6m»
лучше, чем «IMG_3421». Писать можно по-русски — кириллица транслитерируется,
пробелы и знаки превращаются в дефисы: «Бытовка 6 метров, фасад» →
`bytovka-6-metrov-fasad`. Расширение не спрашивается и не меняется: тип файла
задан его содержимым (всё лежит в WebP), а не именем.

Переименование меняет адрес файла, поэтому API заодно переписывает ссылки на
него в товарах, статьях и направлениях — уже расставленные картинки не
отваливаются. Если имя занято другим файлом, панель откажет и скажет, каким
именно: два файла с одним адресом невозможны.

**Это значение по умолчанию, а не единый источник.** Когда файл вставляют в
товар или в блок статьи, описание копируется на место и дальше живёт там своей
жизнью:

- правка описания у товара не меняет медиатеку;
- правка описания в медиатеке не догоняет уже расставленные фотографии.

Так сделано намеренно: одна и та же картинка в каталоге и в статье может
требовать разных слов, а часть фотографий вообще лежит в коде
(`public/renders/...`) и в медиатеке их нет.

## Как правки попадают на сайт

Публичные страницы читают контент из базы через `src/lib/content.ts`.

- Запросы кэшируются (`unstable_cache`) под тегами `products`, `articles`,
  `solutions`, `settings` с ревалидацией 5 минут.
- После успешного сохранения серверный экшен панели сбрасывает нужный тег
  (`revalidateContent` в `src/lib/admin/revalidate.ts`), поэтому публичная
  страница показывает правку **сразу**, а не по таймеру.
- Если API недоступен, страница рисуется на статических данных из
  `src/lib/{site,catalog,blog}.ts`, а в лог сайта уходит строка
  `[content] <ресурс>: показываем статические данные — <причина>`.
  Пустых блоков и падений при выключенном API быть не должно.
- Картинки медиатеки (`/uploads/…webp`) отдаются публичным прокси-роутом сайта
  `src/app/(frontend)/uploads/[...path]/route.ts`; в панели тот же файл
  показывается через `/admin/uploads/*` под авторизацией.

Статья или товар, созданные в панели уже после сборки сайта, открываются по
своему адресу с первого запроса (`dynamicParams` по умолчанию), а несуществующий
slug по-прежнему даёт 404.

**Страница товара живёт по тем же правилам, что и страница статьи.** Адрес —
`сайт.ру/catalog/<slug>`; поле «Slug» в форме товара задаёт его целиком (пустое
поле — соберётся из названия). Товар, снятый с публикации, отдаёт 404 (публичный
список API возвращает только опубликованные), а его адрес пропадает из карты
сайта. Правка товара видна на его странице сразу после сохранения — тег кэша
`products` один и тот же у каталога и у страниц товаров.

> **Смена slug меняет адрес страницы.** Ссылки, которые уже кто-то сохранил или
> отправил, после этого ведут на 404 — переименовывайте slug только у товаров,
> которых ещё нет в выдаче.

### Что важно знать об этой схеме

**Ревалидация раз в 5 минут действует на весь сайт.** Контакты читает корневой
layout, поэтому срок жизни кэша получили все публичные страницы — включая те,
где контента из базы нет вовсе (`/faq`, правовые документы). Практическое
следствие: если API недоступен дольше пяти минут, страницы перерисовываются на
статических данных, и контент, который существует **только** в базе, с сайта
пропадает. Созданная в панели статья в этот момент отдаёт 404 — не потому, что
её удалили, а потому, что сайт откатился к содержимому сборки. Как только API
отвечает снова, всё возвращается само.

**Полностью очистить каталог, блог или направления через панель нельзя.**
Пустой список трактуется как сбой и подменяется статикой из `src/lib/*.ts`.
Если снять с публикации все товары до последнего, на сайте появятся 16 старых
товаров из сборки, а не пустой каталог. Это осознанная страховка (чаще пустой
ответ означает сломанный API, чем намеренную зачистку), но помнить о ней надо:
чтобы убрать раздел с сайта, его нужно убирать из вёрстки, а не опустошать в
панели. То же касается контактов: пустое поле телефона/почты/адреса заменяется
значением из `src/lib/site.ts`.

**Направление без товаров-примеров — законное состояние.** Если убрать из
направления все примеры, на главной вместо карусели появится заглушка
«Примеры для этого направления пока не добавлены» — без пустой карточки и без
стрелок перелистывания. Раньше сайт подставлял на это место примеры из
`src/lib/site.ts`, то есть удалённые товары возвращались сами; теперь правка
панели видна как есть.

**Незнакомые значения фильтров.** Тип, режим эксплуатации, теги и опции товара —
в базе обычные строки, а справочники фильтров каталога остались в
`src/lib/catalog.ts`. Товар со значением, которого в этих справочниках нет, в
каталоге покажется и бейдж выведет, но **ни одним фильтром не отберётся**.

Через панель такое значение больше не создать: все четыре поля выбираются из
справочника — тип и режим эксплуатации выпадающим списком, теги и опции
флажками. Но старые данные с чужими значениями возможны (их могли завести до
этой правки или записать в базу напрямую). Такое значение форма показывает
отмеченным с пометкой **«вне справочника»** и предупреждением, что в фильтрах
оно не участвует: снять его можно, а добавить новое такое — нельзя. Если
значение не трогать, сохранение его не потеряет.

> **Новый тег или опцию из панели добавить нельзя.** Справочники
> `PURPOSE_TAGS` (теги назначения) и `PRODUCT_OPTIONS` (опции) лежат в коде —
> `src/lib/catalog.ts`. Чтобы значение появилось в форме товара и в фильтрах
> каталога, его добавляют туда, после чего сайт нужно пересобрать и выложить.
> Это осознанное ограничение: справочник задаёт фильтры на витрине, и
> случайное новое значение из панели ломало бы подбор товаров. Заявку на новое
> значение адресуйте разработчику.

**После сбоя API сайт выжидает ~10 секунд**, прежде чем снова к нему
обращаться: иначе каждый рендер платил бы полный таймаут. Поэтому поднятый API
сайт замечает не мгновенно, а в пределах этого окна.

## Как приходят заявки

Форма на сайте → `POST /api/lead` (Next) → `lib/lead-delivery.ts` рассылает
заявку по всем настроенным каналам независимо:

**До ответа пользователю** — только то, что ЗАПИСЫВАЕТ заявку:

1. **База админки** — `POST /api/leads` с заголовком `x-api-key`. Включается
   парой `ADMIN_API_URL` + `ADMIN_SITE_API_KEY` в `.env.local` сайта.
2. **JSONL-журнал** — `LEAD_LOG_FILE`, страховка на случай недоступности БД.
3. **Лог процесса** — работает всегда, видно в pm2.

**После ответа пользователю** — уведомления наружу (механизм `after()` из
`next/server`):

4. **Telegram** — токен из окружения (`TELEGRAM_BOT_TOKEN`) + список
   получателей из панели (Настройки → Настройка заявок), с откатом на
   устаревшее одиночное поле и `TELEGRAM_CHAT_ID` из окружения. Каждому
   получателю отправка идёт отдельно.
5. **Почта** — SMTP-доступ из окружения (`SMTP_HOST` + `SMTP_USER` +
   `SMTP_PASSWORD`) + адрес получателя из панели, с откатом на `LEAD_EMAIL`.
   Настроен: отправка с `site@mayak-modul.ru` через `smtp.beget.com`.

Сбой одного канала не мешает остальным. Пользователю экран «Заявка отправлена»
показывается только при успешном ответе эндпоинта, и ответ этот приходит за
десятки миллисекунд: он больше не ждёт ни почтовый сервер, ни Telegram — к
моменту ответа заявка уже сохранена, а уведомления уходят следом. Раньше
зависший SMTP держал посетителя у крутилки все 8 секунд своего таймаута.

В логе процесса рядом со статусом Telegram и почты печатается выбранный адрес
и его источник — так видно, значение взято из панели или из окружения. Строк
теперь **две**, потому что уведомления заканчиваются позже ответа; связывает их
поле `receivedAt`:

```
[LEAD] {"name":"…","receivedAt":"2026-07-28T18:13:21.455Z","delivery":{
  "admin":"ок","file":"ок"}}

[LEAD] уведомления {"receivedAt":"2026-07-28T18:13:21.455Z","phone":"…","delivery":{
  "telegram":"ошибка — 1 из 2 (список в панели): -1001234567890 (Отдел продаж) — ок; 111111111 (Максим) — ошибка: chat not found",
  "email":"ок — получатель: zayavki@example.ru (настройки панели)"}}
```

Первая строка печатается ДО ответа и ни от какой сети не зависит — по ней
заявку можно восстановить, даже если недоступны и база, и файл-журнал.
Отсутствие второй строки означает только «не уведомили», но не «потеряли
заявку».

## Ограничения и что важно знать

- **Модуль генератора ресурсов бэкенда (`app/generate`) удалён.** Он остался
  под MongoDB, а его метод создания ресурса выполнял `prisma db push
  --accept-data-loss`, что рассинхронизировало бы миграции и могло снести
  данные. Маршруты отдают 404.
- **Ограничители частоты живут в памяти процесса.** При нескольких воркерах
  лимит считается на каждый отдельно — на проде нужен общий стор или лимит на
  стороне nginx.
- **Регистрация закрыта:** новых пользователей заводит только администратор
  (`POST /api/auth/register` под админским токеном).
- **Загружаются только растровые изображения** (SVG запрещён намеренно —
  это XML, в который можно вложить скрипт). Всё перекодируется в WebP.
- На проде nginx обязан **затирать заголовок `X-Forwarded-Host`** — иначе
  ослабляется проверка происхождения серверных экшенов Next.

## Обслуживание

```bash
cd react-project-admin-back && npm run seed
```

Сид идемпотентный: приводит контент к эталону, не трогая заявки, медиа и пароль
администратора. Полезен после экспериментов.

Данные он берёт из снимка `react-project-admin-back/prisma/seed-data.json`, а не
из исходников сайта — чтобы работать и на сервере, где каталога сайта рядом нет.
Если эталонный контент в `src/lib/*.ts` изменился, снимок пересобирают:

```bash
cd react-project-admin-back && npm run seed:export
```

**Сид не сбрасывает кэш сайта.** После его прогона публичные страницы могут до
пяти минут показывать прежние данные. Чтобы увидеть результат сразу, сохраните
любую запись в панели — это сбросит нужный тег.

```bash
cd react-project-admin-back && npx prisma studio
```

Прямой просмотр таблиц на http://localhost:5555.

Резервная копия базы:

```bash
docker exec mayak-postgres pg_dump -U mayak mayak > backup.sql
```
